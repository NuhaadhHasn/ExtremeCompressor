## 1. The baseline: 0%, and a false explanation

`.wav` is `Category.AUDIO`, `AUDIO` is in `planner._MEDIA`, so every WAV took
the store route. Measured on the four real WAVs used throughout this document
(335,536,808 B), the archive was the same size as the input. And the reason
shown to the user was:

> media file: already compressed by its codec; stored losslessly so quality is
> untouched (enable Shrink mode to re-encode smaller)

**A WAV has no codec.** It is uncompressed PCM. So 5.07 GiB of real audio
compressed by exactly nothing while being told it was already optimal — the
worst of both, since a user who reads that has no reason to look further.

This is the audio twin of the PNG case B3 found: `_DEFLATE_MEDIA = {".png"}`
exists because a PNG's entropy is deflate output rather than real randomness.
A WAV's entropy *is* real — the four files measure **7.70–7.88 bits/byte**, and
`sample_ratio_max` comes back at **0.991–1.000**, so every entropy heuristic in
the codebase correctly reads "incompressible". Only knowing the **format** tells
you an audio predictor will take 43% off it.

## 2. What the tools already here can do

Before fetching anything. 7-Zip has a **Delta filter** intended for exactly
this — PCM samples correlate in time, so differencing should feed LZMA2
something easier.

| method | bytes | saved | time |
|---|---:|---:|---:|
| store (what shipped) | 335,536,808 | **0.00%** | — |
| `7z -mx=9` default filters | 303,841,523 | **9.45%** | 2.4m |
| `7z -mx=9 -mf=Delta:4` (16-bit stereo) | 325,225,650 | **3.07%** | 1.9m |
| `7z -mx=9 -mf=Delta:2` | 329,918,493 | **1.67%** | 2.3m |

**The Delta filter makes it worse — by a factor of three.** That is the
opposite of the intuition it was tried on, and worth keeping: mastered music is
loud, so consecutive samples are far apart, and differencing *raises* the
entropy it was supposed to lower. Plain LZMA2 at 9.45% is the real bar.

## 3. FLAC, and the flag without which B4 would have been a Phase C item

FLAC 1.5.0 fetched through E1 (see §5). First attempt, plain `flac -8`:

| file | wav | flac | saved | byte-identical |
|---|---:|---:|---:|:--:|
| Aaluma Doluma.wav | 149,396,468 | 79,762,456 | 46.61% | **NO** |
| Thara Local.wav | 133,560,170 | 73,590,020 | 44.90% | **NO** |
| Paisa Paisa.wav | 52,402,078 | 35,191,502 | 32.84% | **NO** |
| ride.wav | 178,092 | 44,540 | 74.99% | **NO** |
| **total** | 335,536,808 | 188,588,518 | **43.79%** | **0 of 4** |

43.79% and not one file identical. On the evidence of B3 and B5 that reads like
a third Phase C item — but the diagnosis is different, and it matters:

```
source   52,402,078 B      decoded   51,943,964 B      difference  458,114
RIFF size field   0x031f9796  vs  0x03189a14     <- differs
data chunk size   0x031899f0  vs  0x031899f0     <- IDENTICAL
```

**The audio is intact; the container is not.** These WAVs carry non-audio RIFF
chunks after the audio, and plain `flac -d` writes a canonical WAV and silently
drops them. FLAC is lossless about *audio*; this project's ledger is about
*files*.

`--keep-foreign-metadata` preserves them:

| file | wav | flac | saved | byte-identical |
|---|---:|---:|---:|:--:|
| Aaluma Doluma.wav | 149,396,468 | 80,532,408 | 46.09% | **YES** |
| Thara Local.wav | 133,560,170 | 74,524,762 | 44.20% | **YES** |
| Paisa Paisa.wav | 52,402,078 | 35,649,700 | 31.97% | **YES** |
| ride.wav | 178,092 | 44,670 | 74.92% | **YES** |
| **total** | 335,536,808 | 190,751,540 | **43.15%** | **4 of 4** |

The cost is exactly accountable: 458,198 bytes on the one file examined above —
the 458,114 bytes of preserved chunks plus framing. **0.64 points of ratio for
byte-identity**, which is not a trade this project gets to decline.

### The comparison that decides it

| method | saved | lossless |
|---|---:|:--:|
| store (shipped) | 0.00% | n/a |
| 7z `-mf=Delta:4` | 3.07% | yes |
| 7z default | 9.45% | yes |
| **flac -8 --keep-foreign-metadata** | **43.15%** | **yes** |

**4.6× better than the best thing already installed.** B4 is the first
specialist in this project to win: B3's `oxipng` (31.79%, 0/10 identical), B5's
`qpdf` (7.14%, 0/10 identical) and K4's wide zstd window (0% on real data) all
lost to the route already present.

The reason is structural rather than lucky, and it predicts the pattern rather
than just fitting it: a PDF or a docx is **already deflate output** one layer
down, which is precisely what Precomp reaches, so a second general-purpose
recompressor has nothing left to find. A WAV is **genuinely uncompressed**, and
no general-purpose compressor models audio at all.

## 4. End to end, through the engine

Three real WAVs, 201,976,638 B, profile `normal`:

```
201,976,638 -> 116,227,778 B    42.45% saved    75.5 s
excmp extract: restored 3 file(s), verified 3 hash(es) OK in 9.8s
independent SHA-256 tree comparison: 0 missing, 0 extra, 0 differing
                                     -> BYTE-IDENTICAL
```

And what the user is now told, from `excmp list`:

```
src/Aaluma Doluma.wav   142.5 MB  store   uncompressed PCM audio: packed with
                                          FLAC, which restores it byte for
                                          byte (measured ~43% smaller)
```

`flacaudio.pack` follows `excmp/jpeg.py` exactly: compress, **immediately
decompress, compare against the original bytes**, and return `None` unless they
match. That doubles the work per WAV and buys the ability to *fall back* rather
than *fail* — a file FLAC would mishandle is caught while storing it raw is
still free, instead of at restore time when D9 would refuse the whole archive.
Files below 4 KiB, non-WAVE RIFF containers (an AVI is also RIFF), truncated
files and anything that encodes *larger* are all declined rather than raised on.

## 5. E1's second fetch, and the hole it exposed in E1

FLAC 1.5.0 was fetched with the E1 downloader. Two things came out of it.

**GitHub had no hash for this asset.** The release predates the per-asset
`digest` field and the API returns `null`. Pinning a hash computed from our own
download would be circular — it proves only that we hashed what we downloaded —
so the pin came from **Microsoft's winget-pkgs manifest** for the identical
URL, and `fetch_tool` then confirmed the downloaded bytes against it. Two
independent parties, which is the standard E1's own roadmap item asks for.

**An audit of E1 then found a critical hole, on this very tool.**
`verify_installed` hashed `exe_relpath` and nothing else. On the real qpdf
install that is **19,456 of 87,686,094 bytes — 0.02%**: `qpdf.exe` is a
launcher and the 7.4 MB `qpdf30.dll` beside it holds the code. Windows searches
the application directory first for a non-KnownDLL, so replacing a sibling is
code execution inside the process the engine spawns.

It was live rather than theoretical **because of B4**: `flac.exe` is 339 KB
next to a 522 KB `libFLAC.dll`, and `flacaudio` spawns it through
`installed_path`. Reproduced on the real install:

```
before the fix:  libFLAC.dll swapped -> verify_installed=True   available=True
after  the fix:  libFLAC.dll swapped -> verify_installed=False  available=False
                 version.dll planted -> verify_installed=False  available=False
```

The first repair attempt was worse than useless and is worth recording: the
expected digest was written to `.pinned-sha256` **beside the binary**, so the
same write that replaces a DLL can rewrite the marker. Hashing the whole tree
into that file fixes nothing for the same reason. The anchor has to live
somewhere the attack cannot reach, so it is now `ToolSpec.exe_dir_sha256` in
source, beside the archive hash that was already trusted that way — and
`verify_installed` additionally refuses **extra** files, because planting
`version.dll` modifies nothing pinned and Windows will still load it.
