# 2026-10-15: B18, three unmeasured settings — measured; two changed, one kept

**Machine:** Dell Inspiron 15-3567, i5-7200U (2 cores / 4 threads), 15.9 GB
(`Win32_Processor` checked). **Every timing below is contended.** Another
development session ran throughout, free RAM fell to 2–4 GB, and one batch
was stopped by Claude Code for low memory and resumed later (§3). All
benchmark processes ran at below-normal priority, checked with
`Get-Process`. Sizes and restore results don't depend on the contention;
times do. **No time here is a pin.**

Harnesses: `C:\excmp-bench\b18\` — `zstd_threads.py`, `precomp_intense.py`
(+ `verify_zpaq.py`), `b18_media.py`, `run_media.py`, `b18_app.py`. Logs
beside them (`*.jsonl`).

## 1. Headline

| | setting | finding | change |
|---|---|---|---|
| (a) | zstd `threads=-1` vs 2 | identical bytes; +184 MiB at `-1`; the timings are too noisy to call | **default kept**; an explicit Worker threads count is now honoured, capped at the default |
| (b) | `precomp -intense` | off saves 0.78% / 0.85% on installers and 0.16% / 0.08% on deflate data, but loses whole raw-zlib streams (−16.8% on a synthetic sample; the suite caught it) | **kept on**; B6's game data decides |
| (c) | MP3/MP4 probe | files the probe flags saved 3.77–9.20% under 7-Zip (group totals); the rest 0.32–1.61% | **`.mp3` and `.mp4` join Ogg** in the probe rule |
| (c′) | MP3 through Precomp | Precomp recodes MP3 itself (packMP3): every MP3 piped at Extreme saved **18.02% / 15.87%** end to end | **every MP3 is piped on a chain with Precomp**, whatever its probe |

## 2. (a) zstd's thread count

`ZstdStage` passed `threads=-1` (every logical processor, 4 here) and ignored
the Worker threads setting. Each setting ran in its own process, which
reported its own peak working set from inside (see §5). Every frame was
decompressed and SHA-256 compared.

**Silesia tar** (12 files, PAX, 211,968,000 B), level 19, LDM, window 2^28,
three pairs, `-1` always run first:

| threads | archive | compress (3 runs) | median | peak RAM |
|---|---:|---|---:|---:|
| **`-1` (ships)** | **52,595,898** | 132.4 / 149.2 / 91.2 s | **132.4 s** | 735 MiB |
| `2` | 52,595,898 | 162.9 / 188.5 / 108.8 s | 162.9 s | 552 MiB |
| `0` (no workers) | 52,611,365 (+0.03%) | 157.7 s | — | 433 MiB |

**Installer tar** (`programs.tar`, 55,743,488 B), one run each:

| threads | archive | compress | peak RAM |
|---|---:|---:|---:|
| `-1` | 46,982,246 | 37.1 s | 265 MiB |
| `1` | 46,982,246 | 22.0 s | 265 MiB |
| `2` | 46,982,246 | 29.5 s | 265 MiB |
| `4` | 46,982,246 | 19.6 s | 265 MiB |
| `0` | 46,984,530 | 38.1 s | 220 MiB |

**Any worker count from 1 up writes the same bytes**; only `0` differs.
**The timings settle nothing.** `-1` was quicker in all three Silesia pairs
(0.79–0.84× the time), but it always ran first. On the installer tar, `-1`
(which is 4 threads here) took 37.1 s and an explicit `4` took 19.6 s: the
same configuration, 1.9× apart, which is more noise than the gap being
measured. (Caught by the review; the first draft called `-1` faster.)

**Decision:** keep `-1` as the default, because the bytes are identical and
nothing measured argues for moving it. The physical-core default came from
7-Zip, where extra threads cost ratio and doubled RAM; zstd's output doesn't
depend on the worker count. 184 MiB on a 212 MB input is well inside
`_RAM_BUDGET`. **What changes:** an explicit Worker threads count now
reaches zstd (it used to be ignored), so "lower it to keep the machine
usable" now holds for Fast too. A count above `-1`'s is capped at it (review:
each worker holds window-sized buffers, and `ram.zstd_compress_ram` was
fitted at `-1`, so 16 workers would exceed the quoted peak). "Auto" (0) keeps
`-1`. Tests: `tests/test_b18_zstd_threads.py`.

## 3. (b) `precomp -intense`, on and off

Both B12 corpora, through both final codecs the app runs after Precomp.
Command lines built by the app's own stage objects (`SevenZipStage`,
`ZpaqfranzStage`, defaults, two threads). Each `.pcf` restored with
`precomp -r` and SHA-256 compared to the original input; each archive
restored and compared to its `.pcf`.

| corpus | | with `-intense` (shipped) | without | difference |
|---|---|---:|---:|---:|
| installers (13 files, `programs.tar`) | `.pcf` | 62,482,862 | 59,895,108 | −4.14% |
| | Extreme, 7-Zip | 46,048,132 | **45,686,925** | **−0.78%** |
| | Insane, zpaqfranz `-m58` | 45,915,379 | **45,523,860** | **−0.85%** |
| deflate (Silesia zip, 64,726,889 B) | `.pcf` | 236,958,376 | 236,956,196 | −0.001% |
| | Extreme, 7-Zip | 51,827,160 | **51,745,074** | **−0.16%** |
| | Insane, zpaqfranz `-m58` | 42,852,397 † | **42,816,077** ‡ | **−0.08%** |

† B17's verified figure. The `-intense` `.pcf` regenerated today hashes
identical to the one B17 compressed (`c0fc71cb…c0984`), so it's the same
input; it wasn't recompressed, to save an hour of CPU on a short-memory
machine.
‡ This run's compress finished, then Claude Code stopped the batch for low
memory before its restore check. The archive was restored and verified
separately (`verify_zpaq.py`, 1,984.8 s, byte-identical); its compress time
is lost.

**Time.** `-intense` on the deflate zip: Precomp took **1,238 s** to compress
and **516 s** to restore, against **146 s** and **58 s** without. Contended
and single runs, but an 8.5× gap is not noise. On the installer tar the two
were close (7.4 s / 6.3 s).

**Why it costs bytes.** Precomp's source study
([research/15](../research/15-source-study-precomp.md) §`-intense`):
it "treats *any* 2 bytes passing the zlib header check" as a candidate stream.
On installers it found and expanded streams that the final codec then
compressed worse than they were (the `.pcf` is 2.6 MB bigger and the
archives 0.8% bigger). B12 had already recorded the 82,086 B it cost on the
deflate corpus under 7-Zip; this measures it everywhere else.

**Decision: kept ON, after first shipping it off.** The branch turned it
off on the numbers above, and the local full suite caught what that broke:
`test_extreme_chain` builds raw zlib streams (no container, the shape of a
game pak) and expects Precomp in the chain. Without `-intense` Precomp finds
nothing in them, skips itself, and Extreme silently becomes Normal. Measured
on synthetic samples (illustrative, not a corpus), through `precomp -cn` →
7-Zip:

| sample | without `-intense` | with it |
|---|---:|---:|
| raw zlib stream, 606,914 B | 241,589 (Precomp found nothing) | **201,094 (−16.8%)** |
| pak-like, zlib chunks mid-file, 201,774 B | 200,678 | 200,791 |

So the trade is under 1% on installers and deflate archives against a
whole-stream loss on raw zlib data, the case `-intense` was added for and
one no real corpus here has measured. It stays on. B6's game data is what
can settle it, perhaps per data type: `PrecompStage(intense=False)` stays
reachable. Tests: `tests/test_b18_precomp_intense.py`. **CI didn't catch this,
because Precomp isn't on the runner**; only the local suite runs that test.

## 4. (c) MP3 and video: does the probe predict a real gain?

B13a showed it does on Ogg: the files whose `sample_ratio_max < 1.0` (zstd-3
over up to three 1 MiB samples) were the ones 7-Zip could shrink.

### The corpora

Found by a read-only search (the owner pointed at `Downloads-1`):

- **MP3, music**: the 5 MP3s in `Downloads-1\Songs`, 33,922,849 B.
- **MP3, misc**: the other 29 MP3s under `Downloads-1`, deduplicated by
  SHA-256 to 16 files, 80,307,437 B: Android app audio resources from
  several copies of one project, ringtones, three downloaded songs, and
  sample tracks from a JS course.
- **Phone video**: 57 files from a Google Photos export on this machine,
  195,869,772 B: all 27 iPhone screen recordings plus a spread of 30 camera
  videos across the probe's range. **51 are MP4 and 6 are MOV**: the probe
  search matched `.mov` too, which the first draft missed (review). The MP4
  figures below are MP4 only; the MOVs are stored by every rule here.
- **Downloaded video**: 9 MP4s, 1,014,440,439 B: the six smallest non-phone
  MP4s the probe flags and three it doesn't. **Recorded by size and ratio
  only; no names or folders.** Two of the six flagged turned out to be one
  70 KB test clip from a source tree, present twice, so the flagged group is
  four real videos (523 MB) plus that clip.

Sources were only read. The MP3s were copied into the bench folder; the phone
videos were hard-linked there for the end-to-end runs.

**The probe, over everything found:** 8 of 21 MP3s flagged (59.2 MB of 114.2
MB). Of 614 MP4s (168.4 GB), 159 flagged (6.10 GB). (The search also found
65 MOV and 4 WebM files, left alone.)

### The codecs, per file, every file restored (7-Zip `-mx9 -mmt2`, zstd 19)

| corpus | all MP3/MP4, 7-Zip | probe flags it | probe doesn't |
|---|---:|---:|---:|
| MP3, music | 3.08% | 3 files, **4.17%** (3.26–7.78) | 2 files, 0.35% |
| MP3, misc | 2.53% | 5 files, **5.24%** (3.29–7.07) | 11 files, 0.45% |
| phone video, MP4 | 6.21% | 40 files, **9.20%** (0.17–25.67) | 11 files, 1.61% |
| downloaded video | 2.10% | 6 files, **3.77%** (2.22–18.44) | 3 files, 0.32% |

zstd 19 beat 7-Zip on every corpus total, by little. Per file, 7-Zip won
some of the camera videos. **The probe separates the group totals on all
four corpora, and per file the groups overlap**: 12 of the 42 flagged phone
files (all with a probe of 0.99 or more) saved under 1%, as little as 0.17%,
and an unflagged screen recording saved 5.81%. The screen recordings are
the extreme case: probe 0.74 and 25.7% off under 7-Zip. Static screen
content is the least random "compressed" video there is.

**Misses on the cautious side:** an unflagged 1.2 MB MP3 still lost 4.0%,
and an unflagged 12 MB screen recording 5.8%. The probe reads at most three
1 MiB samples, so it can miss a file whose redundancy lies elsewhere. That
costs a little saving, never correctness.

### Through the app, before and after

`engine.compress` (D9 self-test included), `engine.extract`, then an
independent SHA-256 of every restored file: **every row restored every
file, 0 mismatches**. "Before" is the same harness with the rule set back
to Ogg only (`b18_app.py --incumbent`).

| corpus | before (stored) | Normal | Extreme, probe rule | Extreme, every MP3 piped | Insane |
|---|---:|---:|---:|---:|---:|
| MP3 music, 33.9 MB | −0.006% | 2.98% | 13.69% | **18.02%** | 13.85% (probe rule); **18.97%** (every MP3) |
| MP3 misc, 80.3 MB | −0.005% | 11.22% | 8.42% | **15.87%** | — |
| phone video, 195.9 MB | −0.005% | **4.68%** | 4.68% | — | — |

Three things in that table were not predicted:

- **MP3 misc at Normal, 11.22%, is mostly one near-duplicate pair.** Two of
  its files are both 7,738,506 B, probe 0.939, not SHA-identical (two copies
  of one app's audio). Per file, 7-Zip predicts about 1.83 MB of the 9.01 MB
  saved; a solid archive collapses the second copy. That's cross-file
  redundancy, which the per-file estimate cannot see (below).
- **Video gains nothing from Precomp**: Extreme is the same size as Normal
  (186,700,879 against 186,699,875), at about 22% more time. So when the GUI
  recommends Extreme for a video folder, it costs a little time and no bytes.
- **MP3 gains a lot from Precomp.** Precomp v0.4.7 recodes MP3 itself: its
  help lists `3 = MP3` among its stream types (packMP3). The probe cannot
  see that, because it measures what zstd finds. Under the probe rule only
  the flagged MP3s reached Precomp, so the **"every MP3 piped"** column was
  run (`--pipe-all-mp3`, the PNG override path): 18.02% and 15.87%, the best
  on both corpora. On misc it also beats Normal's near-duplicate win.

### MP3 through Precomp, file by file

`precomp -cn` on each of the 21 MP3s, `precomp -r` back and SHA-256
compared, then 7-Zip on the `.pcf` exactly as Extreme runs it, restored and
compared (`mp3_perfile.py`). **All 21 restored byte-identically; Precomp
exited 0 on every one and found MP3 streams in every one.**

| | files | packMP3 `.pcf` | chain (`.pcf` → 7-Zip) | per file, chain |
|---|---:|---:|---:|---:|
| music, probe flags it | 3 | −15.98% | **−19.15%** | 18.44–20.73% |
| music, probe doesn't | 2 | +1.57% | **−15.21%** | 10.03–16.22% |
| misc, probe flags it | 5 | −19.36% | **−19.37%** | 13.87–25.93% |
| misc, probe doesn't | 11 | −13.15% | **−13.15%** | 10.66–23.98% |
| **all 21** | 21 | −14.41% | **−16.50%** | **10.03–25.93%**, median 14.31% |

**The probe is irrelevant to packMP3**: the files it doesn't flag saved
10.0% at worst. One music file's `.pcf` came out *larger* than the MP3
(−3.83%) and still lost 16.22% through 7-Zip, so the `.pcf` alone is not the
measure. Precomp took 146.7 s and its restore 275.9 s over the 21 files
(114 MB), contended: about 0.8 MB/s and 0.4 MB/s, **not a pin**.

### The estimate against the app

The estimate's range contained the archive in 6 of 7 runs. The miss is on
the good side: MP3 misc at Normal came out at 71,294,335 B, under the range's
low of 77,180,979. That is the near-duplicate pair: the estimator predicts
each file from its own probe and can't see redundancy *between* files. Any
piped duplicates behave this way; it isn't specific to media. Inside the
range, `expected` was 12–13% pessimistic at Extreme/Insane on music (it
doesn't model packMP3) and 3% optimistic on phone video. B18 then gave the estimator packMP3's measured ratio for an MP3 on a
Precomp chain, `_MP3_PRECOMP_RATIO = (0.74, 0.90, 1.0)`. A first draft used
the byte-weighted average, 0.835. The skeptic reviewer showed that broke a
promise: on a Precomp chain the GUI shows `expected` as a ceiling ("≤ X"),
and 0.835 put "≤ 64.0 MB" over the 64.4 MB misc archive. So `expected` is
the *worst* of the 21 files, 0.90. Every measured run now sits under it:
+9.79% (music, Extreme), +11.08% (music, Insane), +6.98% (misc, Extreme)
above the actual archive, so the ceiling is conservative and honest. An MP3
packMP3 declines can still exceed it; `high` is 1.0 for that.

**The time estimate is still optimistic**: Extreme on the music MP3s
predicted 13–82 s against 180 s measured, and misc about 30–194 s against
298 s. The self-test's restore rate for the Precomp chain is 6.5 MB/s, while
packMP3 restored at 0.07–1.46 MB/s per file. Contention can't explain all of
that gap, but every timing here is contended, so no rate is pinned. It waits
for a quiet machine, with B13's restore re-measure. Until then the
45-minute long-job warning fires too rarely on MP3 folders.

**Decisions:**

- `.mp3` and `.mp4` join `_PROBE_DECIDES` (`excmp/planner.py`). MKV, WebM,
  MOV and M4A were not measured and keep "stored as-is".
- **On a chain with Precomp (Extreme, Insane) every MP3 is piped**,
  whatever its probe: `_PRECOMP_MEDIA = {".png", ".mp3"}`. Without Precomp
  the probe still decides.
- **What it costs: near-duplicate MP3s.** packMP3 recodes each file
  arithmetically, so two near-identical inputs (the misc pair differs in
  3,059 bytes) become unrelated streams. At Extreme the misc archive,
  67,564,664 B, is almost exactly the sum of the per-file results
  (67,575,902 B): the pair's redundancy is gone. With every MP3 piped,
  Extreme still beat Normal on that corpus (15.87% against 11.22%). A
  library made mostly of near-duplicates could go the other way, and the
  estimator sees neither effect.
- **A malformed `.mp3` does not fail the job** (skeptic review, measured):
  a truncated MP3, random bytes, an ID3 tag over garbage and a WAV, all
  named `.mp3`, went through Extreme with one real MP3. The job succeeded and
  all 5 restored byte-identically, 24.4% smaller. The D9 gate makes this safe
  regardless: a wrong restore fails the job, it never publishes. Kept as
  `test_malformed_mp3s_do_not_fail_an_extreme_job`.
- Tests: `tests/test_b18_media_probe.py`. It has a synthetic MP4 round trip
  that runs on CI, two real-file round trips and the estimator bracket on
  three real files (these need the bench samples, so they skip on CI), and
  the routing rules for every profile.

## 5. Things worth not rediscovering

- **The venv's `python.exe` is a launcher.** It starts
  `C:\Python312\python.exe` as a child, so `Popen(...)._handle` on a Python
  child gives **the launcher's** memory counters: 4 MB for a zstd level-19
  job that really peaked at 171 MiB. Measure a Python child from inside it
  (`GetProcessMemoryInfo(GetCurrentProcess())`, typed), as
  `zstd_threads.py` now does. Native tools (7-Zip, zpaqfranz, darc) are
  direct children and were measured correctly. The repo's own peak figures
  (`ram.py`) were measured in-process and are unaffected.
- **Untyped ctypes `SetPriorityClass(GetCurrentProcess(), …)` silently fails**
  (returns 0, `ERROR_INVALID_HANDLE`): see the B14 record. `start /belownormal`
  in a `.cmd`, or `creationflags=BELOW_NORMAL_PRIORITY_CLASS`, both work and
  were checked with `Get-Process`.
- **Claude Code reaps background shells when the machine runs critically
  short of memory**, and the note says not to restart them unasked. Log
  each row as it lands (every harness here does), so a reaped batch loses
  only the row in flight.
