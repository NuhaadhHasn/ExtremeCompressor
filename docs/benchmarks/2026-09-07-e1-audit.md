# E1 — the audit, verified one claim at a time

**2026-09-07**, this laptop. E1 (`excmp/toolfetch.py`) shipped, was then
audited adversarially, and the audit reported **39 findings across four
lenses** before running out of session with only 6 of its 44 agents finished.

One finding had been verified with a reproduction. The rest were **leads**, and
this document is what happened when each was checked by running it rather than
by reading it. That distinction is the project's standing rule and it earned its
keep here: **10 of 12 distinct claims reproduced, 2 did not**, and two more
turned out to be *my own test artifacts* rather than defects.

Harness: `scratchpad/verify_e1.py` — one function per claim, each printing what
it actually observed. Every fix below has a regression test in
`tests/test_toolfetch.py`, which went 20 → 36 tests.

---

## 1. The one that was already verified, and the worst of the batch

**`verify_installed` guarded 0.02% of the install.** It hashed `exe_relpath`
and nothing else. On the real qpdf install that is **19,456 of 87,686,094
bytes**: `qpdf.exe` is a launcher and the 7.4 MB `qpdf30.dll` beside it holds
the code. Windows searches the application directory first for a non-KnownDLL,
so replacing a sibling is code execution inside a process the engine spawns.

**B4 made it live rather than theoretical.** `flac.exe` is 339 KB next to a
522 KB `libFLAC.dll`, and `flacaudio` spawns it through `installed_path`:

```
before:  libFLAC.dll replaced -> verify_installed=True   available=True
after:   libFLAC.dll replaced -> verify_installed=False  available=False
         version.dll planted  -> verify_installed=False  available=False
```

**The first repair was no better, and that is the instructive part.** The
expected digest was written to `.pinned-sha256` *beside the binary*, so the same
write that swaps a DLL rewrites the marker — confirmed, it left
`verify_installed` returning True. Hashing the whole tree into that file fails
for the identical reason. **A trust anchor inside the thing it protects is not
an anchor.** It now lives in source (`ToolSpec.exe_dir_sha256`), covers every
file in the executable's directory, compares case-insensitively because Windows
resolves DLLs that way, and refuses **extra** files — planting `version.dll`
modifies nothing pinned and the loader would still take it.

## 2. Reproduced, and fixed

| # | claim | measured |
|---|---|---|
| F | **no bound on unpacked size** | a **204,060-byte download installed 209,715,202 bytes — 1028×**, no refusal |
| J | `spec.size` not used as a streaming bound | 41,943,160 B written for a **120-byte** pin before the check fired |
| O | unverified bytes staged inside the install root | 209 MB of a *refused* download left under it |
| B | `ensure_tool` raises what it documents as swallowed | `BadZipFile` and `UnsafePathError` escaped it |
| D | `fetch_tool(allow_insecure=True)` by default | "HTTPS only" was opt-in on the function doing the work |
| G | a pre-release outranks its release | `_version_tuple("1.5.0-rc9") > ("1.5.0")` → **True** |
| Q | duplicate entry names accepted | two entries for one name, **the second won** |
| K | `_redirect_ok` compared `netloc` | `github.com → …githubusercontent.com:443` **refused** |
| R | the version floor was unset | `min_version=''` on **both** shipped entries |
| P | `find_tools` did not know E1's layout | a pinned tool was invisible to normal discovery |

Notes on the ones where the fix was not obvious:

**F, the bomb.** A ceiling on the compressed side is not a ceiling — that is the
whole point of a zip bomb. The first replacement constant was **768 MiB, which
sat above the 209 MB bomb that had just been measured**, so it caught nothing;
picking a limit without checking it against the thing it is meant to stop is
decoration. It is 256 MiB, above qpdf's 87.7 MB install and an FFmpeg build,
with an entry-count cap too, enforced on the real stream rather than on
`file_size` headers. Worth stating plainly: **the hash pin is the primary
defence** — with a correct pin the archive content is fixed and cannot be
attacker-chosen — and this ceiling is the backstop for a manifest typo or a pin
taken in good faith from a bad source.

**G, the version floor.** Stripping non-digits per chunk turned `1.5.0-rc9`
into `(1, 5, 0, 9)`, which sorts *above* `1.5.0`. A floor of "1.5.0" would have
accepted a release candidate of itself, and the floor exists to keep
known-vulnerable builds out. Now everything from the first non-numeric chunk is
dropped and a release/pre-release marker appended, so `1.5.0-rc9 < 1.5.0`.

**K, an availability bug inside a security check.** Refusing legitimate
redirects is how security checks end up switched off. `netloc` carries the port
and the case; the comparison is now on the bare hostname, taken from *after* the
last `@` so `github.com@evil.com` resolves to `evil.com` and is refused.

**P, quietly broken.** `tools.py` promised to look "in the app-managed
`tools/bin` directory" and only ever checked a flat `tools/bin/<name>.exe`,
never E1's nested `<name>/<version>/<exe_relpath>`. Nothing *appeared* broken
because `flacaudio` asks `toolfetch` directly — the discovery layer simply did
not know the tool existed. `find_tools` now consults the manifest through
`installed_path`, so a fetched tool is reported only while it still matches its
pin.

## 3. Not reproduced

**M — "an absolute `exe_relpath` escapes the install dir".** It does not:

```
exe_relpath = "C:/Windows/System32/cmd.exe"
  -> UnsafePathError: unsafe archive path: drive letter
  verify_installed -> False    installed_path -> None
```

`_exe_in` goes through `resolve_within`, which is the D0 validator, and it
holds.

**A — "only the last redirect hop is checked".** The claim as stated did not
reproduce: the fetch was refused. But the *underlying* observation was correct
and worth acting on — `urlopen` follows a chain internally and `geturl()`
reports only where it ended, so an intermediate `Location` naming any host was
contacted before anything looked at it. A `HTTPRedirectHandler` subclass now
validates **every** hop for both scheme and host. Recorded as a fix prompted by
a claim that was right about the mechanism and wrong about the consequence.

## 4. Two findings that were my own tests, not the code

Recorded because they are the failure mode this document is about, inverted.

After the fixes, the harness still reported F and A as CONFIRMED. Neither was:

- its **F** case built a 200 MiB bomb, which is *under* the new 256 MiB
  ceiling, so passing was correct;
- its **A** case relied on two different *ports* on `127.0.0.1` standing for
  two different hosts — and the K fix strips ports, correctly, so they became
  the same host.

**A harness that is not updated alongside the code starts reporting the code's
correctness as a defect.** The same discipline that says "reproduce before you
believe" says "re-read the reproduction before you believe it twice".

## 5. Reproducing all of it

```
.venv\Scripts\python.exe -m pytest tests\test_toolfetch.py -q
```

36 tests. The hostile cases are served from a localhost `http.server` —
hermetic, offline, and able to send deliberately corrupt bytes, which is the
half that matters. `allow_insecure` is waived in exactly one test helper, so
the production default stays False and every waiver is visible.
