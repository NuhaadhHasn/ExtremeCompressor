# K1 — the manifest cap: measurements

**2026-09-04**, extended and re-measured **2026-09-06/07**, branch
`phase-k1-manifest-v2`, this laptop (2-core i7-3540M, 16 GB, Windows 10 Pro
19045).

Everything here was reproduced before it was written down. Several figures from
the first pass did **not** reproduce on the second and have been corrected in
place, each with a note saying so — §1's DEFLATE row, §2's parse time, §3's
reason-table bound. The rule that produced those corrections is the same one
that produced K1: measure the artifact that actually ships, not a stand-in for
it. §6 is the authoritative end-to-end.

---

## 1. The manifest, on the tree that could not be archived

`...\Programming Tutorials, Guides, Course, and Files\5React, ReactNative`
— **57,020 files, 33.83 GiB**, walked read-only. The manifest was built from
those **real relative paths** with a representative store reason, and
serialised.

| manifest shape | bytes | | vs cap (8 MiB) |
|---|---:|---|---|
| v1, as shipped before K1 (`indent=2`) | 42,858,112 | **40.87 MiB** | ⛔ 5.1× over |
| − `routes[].files` | 33,504,002 | 31.95 MiB | ⛔ 4.0× over |
| − `store_reasons` | 16,851,332 | 16.07 MiB | ⛔ 2.0× over |
| − `indent` (compact separators) | 14,855,559 | 14.17 MiB | ⛔ 1.8× over |
| **v2 as shipped (interned reasons)** | 15,482,955 | **14.77 MiB** | ⛔ 1.8× over |
| **DEFLATE(6) of the v2 document** | 794,979 | **0.76 MiB** | — |

⚠️ **The DEFLATE row is optimistic by ~5× and must not be used as the
compression factor.** Every ledger entry here carries a *synthetic* sha256
(`f"{i:064x}"`, and the earlier pass used `"0" * 64`), and a column of
near-identical hashes deflates to almost nothing. Real hashes are random hex
and set a floor no deflater can go under: 55,477 × 64 chars is 3.5 MB of
incompressible text on its own. The real archive in §6 deflated its manifest
**12,782,745 → 2,720,064 B, a factor of 0.213** — not 0.045. That mattered:
`estimate._MANIFEST_DEFLATE_FACTOR` had been set to 0.10 on the strength of
the synthetic figure, which *under*-booked disk in a preflight whose whole job
is to over-book it. It is now 0.30.

⚠️ **Read the top two rows as a worst case, not as the number a real job
produced.** They model *every* file as stored and carrying the 132-character
media sentence, and the two rows that depend on that assumption are the only
two sensitive to it — everything from `− store_reasons` down agrees to within
100 bytes with the run that first measured this table on 2026-09-04, while the
v1 rows came out 3.59 MB (63 B/file) larger here purely because a different
representative sentence was used. In an actual compress of this tree most files
**pipeline** and carry no store reason at all. §6 has the authoritative figure:
the exact v1 document for a real job, reconstructed from that job's own v2
manifest, where the real routing decides who carries a reason.

### Two corrections to the plan

**The roadmap said "~29 MiB". It is 40.87 MiB** on this model, and the roadmap's
29 MiB matches the size *after* `routes[].files` is removed — so it had been
measured on a partial structure rather than on what the shipped code wrote.

**Schema v2 alone does not fix K1.** All three savings the roadmap listed,
applied together, land at 14.77 MiB — still 1.8× over the cap. The reason is
structural and no field can be trimmed to escape it:

```
57,020 files, 33.83 GiB
relpath average = 152.0 bytes   (max 263)
relpath total   = 8,669,786 bytes
```

**8.67 MB of that manifest is pure path text**, which clears an 8 MiB cap
before a single other field is written. So v2 removes the redundancy *and* the
cap rises.

## 2. What the cap was actually protecting against

The cap exists so an unbounded `json.loads` on attacker-supplied bytes is not a
free memory bomb. `8 << 20` was never measured against that. It is now:

```
json.loads(14.8 MiB of v2 manifest, 57,020 entries)
  1.20 s          (1.2-1.7 s across runs; the machine has 2 cores and the
                   figure moves with whatever else is on them)
  32.1 MiB resident, 33.9 MiB peak   (tracemalloc, object still held)
  = 2.2x the JSON size, 590 B per file
```

So `64 << 20` costs **~139 MiB and ~5 s** worst case, on a machine that already
budgets ~2 GB for one LZMA2 dictionary at `-md=192m`. It covers roughly a
quarter of a million files at this corpus's path lengths, and it is still a
hard bound.

**Corrected from the first pass at this table**: the memory figure reproduced
(31.8 → 32.1 MiB, 2.2×), but the original 0.53 s did not, and the `~2.3 s`
projection built on it was therefore optimistic by about half. Read the time as
1.2–1.7 s for 14.8 MiB. Also worth recording so it is not re-measured wrongly a
third time: `tracemalloc.get_traced_memory()` reports ~0 B resident unless the
parsed object is still referenced when it is called, which is how a 32 MiB
allocation can be made to look free.

## 3. This was never a one-folder problem

Every folder in the tutorial corpus, walked 2026-09-04. `~v1` and `~v2` are the
per-entry model applied to the real path bytes.

| folder | files | path bytes | ~v1 | ~v2 |
|---|---:|---:|---:|---:|
| `5React, ReactNative` | **57,020** | 8,669,786 | **40.87 MiB** ⛔ | 14.77 MiB |
| `7Python` | 12,701 | 1,500,405 | **7.11 MiB** ⚠️ | 3.10 MiB |
| `Mosh Hamedani - All Courses Pack` | 2,272 | 268,017 | 1.27 MiB | 0.55 MiB |
| `1ODOO` | 780 | 72,374 | 0.38 MiB | 0.17 MiB |
| `3C#` | 764 | 81,208 | 0.40 MiB | 0.18 MiB |
| (16 more) | ≤ 329 each | | ≤ 0.21 MiB | |
| **all 21 as one job** | **74,648** | | **~46 MiB** ⛔ | ~19.5 MiB |

**`7Python` sat at 7.11 MiB against an 8 MiB cap** — one folder-growth from
breaking. And the whole corpus as a single selection was refused too. The
roadmap's "1 of 21 folders" was true but read as narrower than it was.

Reasons are cheap to intern because `planner.store_reason` cannot produce many
of them: one fixed media sentence, plus one per two-decimal entropy value from
`ENTROPY_STORE_THRESHOLD` to 8.00. **Corrected 2026-09-06** — this said "≤52
distinct strings, 5,283 bytes", which is the figure for a 7.5 threshold. The
planner uses **7.9**, so the entropy sentences run 7.90…8.00: eleven of them,
twelve with the media sentence, and **1,232 bytes of table** however many files
there are. Enumerated, not reasoned about, and now pinned by
`test_the_reason_table_cannot_grow_past_twelve_sentences`. The real end-to-end
archive in §6 used **7** of the twelve.

pre-K1 expression               : 0

Consistent with `~/.excmp/calibration.json` not existing on this machine.

test_calibration_records_a_finished_job_from_any_working_directory`, which

## 4b. The preflight estimate under-read its own manifest by 24%

Found 2026-09-06 while auditing the K1 change, before it was committed, and
fixed here. **The preflight measured a manifest that is not the one that gets
written.**

`Manifest.new` produces the document `manifest_size_estimate` is modelled on.
`write_container` then mutates the *same* ledger twice more, after the estimate
has already decided the job may proceed:

- **G9 dedup** stamps every duplicate stored entry with
  `,"same_as":"<the other file's whole relative path>"` — 13 bytes plus a full
  relpath, which in this corpus averages 152 and reaches 263;
- **B2** stamps every packed JPEG with `,"codec":"lepton"` — 17 bytes.

Measured on 5,000 stored files whose relative paths are all duplicates of one
another:

| | bytes | vs estimate |
|---|---:|---|
| estimate, as K1 first shipped it | 1,076,178 | — |
| really written, no duplicates | 984,155 | 1.094× — fine |
| **really written, all duplicates** | **1,419,068** | **0.758× — under-reads by 24%** |

That is K1 itself, reached by a different door: an under-reading preflight
waves the job through and the refusal lands back at `write_container`, after
every byte has been written. A folder of media with a duplicated subfolder is
exactly the shape that triggers it, and exactly the shape G9 was built for.

The fix budgets both keys, using the longest name in the selection, because
*which* files turn out to be duplicates is not knowable until they have all
been hashed — which is most of the job. The price is that the estimate is now
deliberately pessimistic: **2.08×** the real v2 manifest on the 57,020-file
tree with every file treated as stored (30.68 MiB predicted against 14.77 MiB
written), which still leaves the 64 MiB cap covering that tree twice over.
Pinned by `test_the_size_estimate_survives_what_write_container_adds_afterwards`.

The general lesson, which is the same one K1 started with: **a preflight has to
model the artifact that is actually produced, not the one its own module
builds.** Both halves of this defect are a check reading a different object
from the one it is protecting.

## 5. v1 archives, proven against real pre-K1 bytes

Not a synthetic stand-in. A worktree was checked out at the pre-K1 commit, an
archive written with **that** code, and then read back with the K1 build:

```
written by the pre-K1 build:
  schema            : 1
  store_reasons     : present, 2 entries
  routes[].files    : [2, 2]        <- every path named a second time
  reasons           : absent
  manifest.json     : compress_type 0 (STORED)

read back by the K1 build:
  restored 4 file(s), verified 4 hash(es) OK in 0.3s
  independent SHA-256 tree comparison: IDENTICAL

  excmp list:
    src/other.bin   store     high-entropy data (7.97 bits/byte): ...
    src/rand.bin    store     high-entropy data (8.00 bits/byte): ...
    src/notes.txt   pipeline
    src/sub/more.txt pipeline
```

The two stored files kept **their own** reasons — 7.97 and 8.00 bits/byte, not
the joined group summary — which is `Manifest.reason_for` falling through from
v2's interned table to v1's per-file `store_reasons`. That is the behaviour
`store_reasons` was added for in the first place, and dropping the field from
the dataclass would have turned every one of these archives into a `TypeError`.

## 6. End-to-end — the folder that could not be archived, archived

**2026-09-06/07.** Not a fixture and not a model: the `node_modules` subtree of
the corpus that broke, compressed, verified, extracted and then compared
against its source by an SHA-256 walk that does not ask the engine's opinion.

```
ReactNative - Practical Guide - Files
  55,477 files, 354,988,110 B (338.5 MiB), profile: normal
```

### The archive

| | |
|---|---:|
| original | 354,988,110 B |
| archive | 101,576,020 B |
| **saved** | **71.39%** |
| compress | 137.5 min |
| `excmp verify` | 24.5 min — **OK, 55,477 restored, 55,477 hashes verified** |
| `excmp extract` | 18.3 min — **55,477 files, 55,477 hashes OK** |
| `excmp list` | 1.2 s |

### The restore, checked independently

```
source   : 55,477 files
restored : 55,477 files      (both trees hashed in 19.1 min)
missing  : 0
extra    : 0
differing: 0
VERDICT  : BYTE-IDENTICAL
```

### The manifest — v1 against v2, on one real job

The v1 document is **reconstructed from this job's own v2 manifest**, so the
real routing decides who carries a store reason. That is what makes it a
comparison rather than a model:

| | bytes | | |
|---|---:|---|---|
| **v1 manifest** | 22,611,183 | 21.56 MiB | ⛔ **2.7× over the old 8 MiB cap** |
| **v2 manifest** | 12,782,745 | 12.19 MiB | ok against 64 MiB |
| **v2, deflated in the container** | 2,720,064 | 2.59 MiB | |

**v2 is 1.77× smaller uncompressed and 8.3× smaller on disk.**

**22,611,183 is byte-for-byte the number in the pre-K1 build's own error
message** (`manifest.json declares 22611183 bytes, over the 8388608 byte
limit`). Two things follow, and neither was assumed: this is the folder that
failed, and the reconstruction is exact rather than approximate.

### Everything K1 claims, observed on this run

| claim | observed |
|---|---|
| schema is v2 | `schema: 2` |
| `routes[].files` is gone | absent; `[('pipeline', 52632), ('store', 2845)]` |
| reasons are interned | **7** distinct sentences, 738 B, for 2,845 stored files |
| the manifest is DEFLATED | `compress_type 8`, 12.19 MiB → 2.59 MiB |
| the preflight over-reads | 13,916,498 B predicted vs 12,782,745 written = **1.09×** |

That last row is the one worth keeping. The preflight has to err high or it
re-creates K1, and the worst-case `same_as` term added in §4b costs **2.08×**
on a tree where every file is stored — but on a *real* job, where only 2,845 of
55,477 files take the store route, the same formula lands at **1.09×**. The
pessimism is paid where it is cheap and is nearly absent where it is not.

## 7. A defect the end-to-end found that no test could

Recorded here because of *how* it surfaced: not from an assertion, but from
listing the temp directory after the run and noticing two scratch folders that
should not have been there. Each held the same 11 files:

```
excmp-verify-i05n75qg/restore/.../rn_first_app/.git/objects/18/1f3cee...
    attrs = ReadOnly, Archive
```

Git writes loose objects **read-only**, and `shutil.rmtree(ignore_errors=True)`
cannot delete a read-only file on Windows — it swallows the error and walks
away. Reproduced standalone, nothing to do with this codebase:

```python
os.chmod(f, stat.S_IREAD)
shutil.rmtree(d, ignore_errors=True)
d.exists()      # True, with objects/18/deadbeef still in it
```

Any compress or extract of a tree containing a `.git` — or any read-only file —
leaves debris on every run, at **11 call sites** that all pass `ignore_errors`.
D3 already asserts temp is clean and D2 already round-trips read-only
attributes; nothing crosses the two, so 945 passing tests sit on top of it.
Filed as **K5** in `ROADMAP.md`; out of scope for K1, and cheap to fix.
