# 2026-10-15: B14, DArc 3.0.4 against the shipped route — measured, not integrated

**Machine:** Dell Inspiron 15-3567, i5-7200U (2 cores / 4 threads), 15.9 GB
(`Win32_Processor` checked). **Every timing below is contended.** Another
development session ran on this machine throughout (67% CPU load and 2.9 GB of
free RAM before the first run), and each DArc process ran at below-normal
priority, apart from the first two minutes of Silesia `-m9` (§5). Sizes and
restore results don't depend on that; times do. **No time here is a pin.**

**Tool:** DArc **v3.0.4** (`github.com/DavidLee18/DArc`, 2026-08-27),
`darc-3.0.4-windows-amd64.zip`, 5,032,728 B, SHA-256
`112d021f2ffc981bddb4a94f34f56118ae48f8d40b4e18772a27892a4747b83a`, which is
GitHub's published digest, re-checked today. Inside: `darc.exe`
(`33538f896358d7ff4f81cf4c73e8c413b9b2af117e2653e20bbce4ba8bfd6b58`) and
`unarc.exe` (`3fce99098e3120bd6e71bff74b9b2601f2b3f1d3eb65aa107e7143e9e5e4a70a`).
GPL-3.0, a Rust rewrite of FreeArc. Every run passed `-cfg- -env-`, so no
stray `darc.toml` or `$DARC` could change the method.

**Harness:** `C:\excmp-bench\b14\b14_run.py` → `b14-results.jsonl`. Each
archive was restored with **`unarc x`** (the separate extractor, not `darc`
itself) and every restored file was SHA-256 compared with its source before
the size was allowed to count. Peak RAM is `PeakWorkingSetSize` from the
exited process handle, the B12 method.

---

## 1. Headline

**DArc loses to Insane on every corpus, by 1.37% to 27.80%, and wins against
Extreme on only one of three.** B14 closes as measured and not integrated.
Nothing was pinned in `TOOL_MANIFEST`, and no stage was written. B12a (plain
FreeArc), which B14 carried, closes with it: DArc is the maintained FreeArc,
and its strongest methods are below.

## 2. The rows (all 8 restored byte-identically by `unarc`)

The inputs are the B12 intermediates, which are what DArc would actually be
fed in the chain: `fresh.pcf` (Silesia zip → `precomp -cn -intense`,
236,958,376 B) and `programs.pcf` (13 installers → same, 62,482,862 B). Plus
the 12 raw Silesia files (211,938,580 B), where DArc picks its own method per
file group.

The incumbents are Insane's `zpaqfranz -m58` (B17: 42,852,397 / 45,915,367 B)
and Extreme's `7z -mx9 -mmt2` (B12: 51,827,136 / 46,048,116 B). For Silesia
they're the end-to-end archives, Insane 37,542,028 B (B17) and Extreme
46,521,346 B (B8). Those include the container and are therefore an upper
bound on the incumbent's payload, so a DArc loss against them is conclusive.

## 3. What the methods are

`--print-config`, which the README documents, is refused by the binary
("not implemented"). The method table was read instead from `darc lt` on a
calibration file:

- **`-mx` is `-m9`.** Byte-identical archives on a 5 MB text file and on a
  16 MB slice of the installer `.pcf`.
- **`-m9` on binary** is `rep` + `exe` + `delta` into LZMA, with the
  dictionary sized to the input. **On text** it is `dict` + `lzp` + **ppmd
  order 22 with a 1 GB model**.
- **`-m9x`** drops `rep` and uses LZMA everywhere. Worse on text (431,622 B
  against 360,876 on the calibration file). On binary it was 1,179 B smaller
  on the 16 MB slice and 16,321 B larger on the whole installer `.pcf`.
- **ppmd is capped at 1 GB**: `-mppmd:24:2gb` was silently rewritten to
  `ppmd:20:1gb`.
- **What it cannot write:** `-mcm` ("needs cm for the default file type,
  which this port cannot write yet") and **`-max`**, which needs ppmonstr
  (`pmm:25:2047m:r1`) for text. Both exit **2** and write no archive, so
  DArc's exit code was honest in every failure seen here.

So DArc's ceiling is ppmd for text and LZMA for binary. Neither is a context
mixer, and `zpaqfranz -m58` is one, which is the whole of the gap on the
deflate corpus.

## 4. Why not even as an Extreme option

DArc's only win is 1.00% under Extreme's 7-Zip on deflate-rich data. The
same argument that closed LOLZ (B12 round 3) applies, more strongly:

- Someone who wants smaller than Extreme on that data gets **16.5% under
  DArc by choosing Insane**.
- On installers and on Silesia it loses to Extreme as well, so it could only
  ever be routed per data type. That means a third codec in the chain for
  1% on one class of data.
- The winning chain is ppmd, which is symmetric: **554 s to restore against
  557 s to compress**. The D9 gate replays every restore before publishing,
  so the user would wait for it twice.

## 5. Things worth not rediscovering

- **DArc picks its method by file extension.** A `.pcf` is filed under
  binary and gets LZMA. The 12 Silesia files have no extension and were all
  filed under text, including the binary ones (`mozilla`, `x-ray`, `sao`).
  Forcing the text chain onto the deflate `.pcf` took 6.3% off `-m9`.
- **A bigger `bsc` block was worse here**: 229 MB blocks gave 52,832,385 B
  against 51,331,204 at the default 25 MB, for 2.6× the peak RAM.
- **Priority did not inherit.** The harness lowered its own priority class
  to below-normal, and `darc.exe` still started at Normal. Why wasn't
  investigated. Both the B14 and B18 harnesses now pass
  `BELOW_NORMAL_PRIORITY_CLASS` to every child explicitly, and that was
  checked with `Get-Process`. The first two minutes of Silesia `-m9` ran at
  Normal before it was caught and lowered by hand. **Check a benchmark's
  priority with `Get-Process`; don't assume it.**

## 6. Reopening conditions

DArc's own errors say it "cannot write yet" ppmonstr and cm, which reads as
unfinished rather than dropped, though no roadmap was checked. If a later
release writes `-max` or `-mcm`, it's worth one rerun of the deflate
`.pcf` against `-m58`, since those are the context models that could close
the gap. Nothing short of that changes the verdict.
