# K2–K5 — the remaining confirmed defects: measurements

**2026-09-07**, branch `phase-k2-k5-defects`, this laptop
(2-core i7-3540M, 16 GB, Windows 10 Pro 19045).

Four roadmap items in one pass: K2 (timestamps + empty directories), K3 (locked
files), K4 (the zstd window) and K5 (the temp leak K1's end-to-end uncovered).

Everything below was reproduced before it was written down. **Five of the
plan's numbers did not survive that**, and they are corrected in place with a
note each. The pattern is worth naming, because it is the third session in a
row to show it: a measurement taken on a *stand-in* — a synthetic corpus, a
placeholder hash, a partial data structure — predicts the stand-in, not the
product.

---

## 1. End-to-end, on real installers

The corpus is chosen so K4 cannot flatter itself: two builds of the **same**
installer, `mysql-installer-community` 8.0.35.0 and 8.0.43.0, 288.6 + 354.2 MiB.
Whatever they share sits ~288 MiB apart — far beyond the 128 MiB the old
`window_log=27` could see, so it was invisible before K4 and no synthetic data
is needed to show it.

```
corpus  : 2 files, 674,115,584 B (642.9 MiB)
          288.6 MiB  2023-11-14  mysql-installer-community-8.0.35.0.msi
          354.2 MiB  2025-08-10  mysql-installer-community-8.0.43.0.msi

compress: 0.9 min   verify: 0.3 min   extract: 0.4 min   compare: 0.2 min

independent SHA-256 comparison (not the engine's own verdict):
  source 2 / restored 2 files
  missing 0 | extra 0 | differing 0        ->  BYTE-IDENTICAL

K2  dates on the restored files:
  ok  8.0.35.0.msi: 2023-11-14 00:29:20  (expected 2023-11-14 00:29:20)
  ok  8.0.43.0.msi: 2025-08-10 22:29:56  (expected 2025-08-10 22:29:56)

K5  temp after compress + verify + extract:  clean
```

Both files restored to their real download dates, exact to the nanosecond;
nothing was left in temp. `excmp verify` and `excmp extract` each independently
re-hashed both files.

⚠️ **Read the archive's own ratio honestly.** The CLI reported
674,115,584 → 674,116,500 B, i.e. **916 bytes larger** and `-0.0%` saved. That
is correct behaviour, not a defect: two already-compressed MSIs are
high-entropy, so the analyzer routes them to `store` and the 916 bytes are
container overhead. It is also the single most important fact about K4 — see §4.

## 2. K2 — timestamps and empty directories

Reproduced 2026-09-04, fixed here:

```
text.txt  (pipeline route)  ->  2023-07-31   tar carries mtime
rand.bin  (store route)     ->  2026-09-04   today
emptydir/                   ->  did not come back at all
```

**The plan said to teach the store route to set mtimes. That would have been
wrong, and the reason was only visible once it was built.** Mtimes are applied
in one pass at the end of `engine.extract`, from the ledger, for *both* routes:

1. The two routes disagreed precisely because each half looked reasonable on
   its own. One pass over the ledger makes them agree by construction.
2. **It has to run after F4's Mark-of-the-Web propagation.** Writing a
   `Zone.Identifier` alternate data stream updates the host file's last-write
   time on NTFS, so a timestamp set inside `extract_stored` is silently
   overwritten by the zone marker a few lines later. Pinned by
   `test_the_zone_marker_does_not_clobber_the_restored_date`, which marks the
   archive first so the propagation path actually runs — without that the test
   would pass for the wrong reason.

`mtime_ns` rides on the `stat()` `analyze_file` already performs. A second walk
would have cost minutes on a 55,000-file tree over the external drive.

Empty directories are a *different* bug one layer up: `iter_files` keeps only
`p.is_file()`, so a directory with nothing in it never enters the ledger. They
travel in a new defaulted `dirs` field — still schema v2, no v3 — holding only
**wholly** empty directories, because a directory with files is already implied
by their paths and a chain is rebuilt from its deepest member. Recording the
shallow ones too would repeat information the paths already carry, which is the
redundancy K1 spent a whole phase removing.

`verify_restore` deliberately does **not** compare timestamps. Every pre-K2
archive lacks them, and "your archive is corrupt" is a far worse outcome than
"your file is dated today".

## 3. K3 — one locked file no longer kills the job

Reproduced with `CreateFileW(dwShareMode=0)`, the way Outlook and Excel hold a
file open. Six files, one locked: the five readable ones are archived, restore
and verify; the sixth is reported by name in `CompressResult.skipped` and
summarised in `warnings`.

**The plan was right about the behaviour and wrong about the location.** It
reads as though the fix belongs where the file is copied. It does not:
`analyzer.analyze_file` **opens every file** to sniff its category and sample
its entropy, and that happens during collection — before the plan exists,
before the ledger, before any staging copy.

Two later windows are guarded as well, because a file readable at analysis time
can be locked before it is hashed or copied, and analysing a large tree takes
minutes. A file dropped in either window must leave **the ledger and both route
lists**; leaving it in the ledger would make D9 refuse to publish an archive
whose ledger promises a file the payload does not contain — turning a graceful
skip into a total failure one stage later.

One deliberate wording choice: the stdlib renders a share-mode denial as
"Permission denied", which is actively misleading on Windows. The user's
permissions are usually fine and the real cause is another program holding the
file open — closing Excel fixes it, changing an ACL does not. So
`describe_unreadable()` says *"in use by another program (or not readable)"*.

Skipping everything is not success: `_nothing_readable()` replaces the bare
"nothing to compress", which would read as "the folder was empty" — the one
thing it was not.

## 4. K4 — the zstd window, and why it is not a free win

The roadmap's synthetic measurement **reproduced to within 4 bytes**:

| window_log | output | predicted | compress |
|---|---:|---:|---:|
| 27 | 314,580,006 | 314,580,010 | 115.3 s |
| **31** | **157,699,989** | 157,699,992 | **74.8 s** |

**49.9% smaller.** Three of the plan's other claims did not survive:

| the plan said | measured |
|---|---|
| 2.1× faster | **1.54×** |
| peak working set *fell* (1,707 → 1,644 MiB) | **rose**, 1,002 → 1,813 MiB |
| raising only compress breaks old readers | ✅ confirmed exactly |

### Two mistakes made while measuring this, both worth recording

1. **A corpus of one repeated 1 MiB block scores identically at every window.**
   LDM finds matches every megabyte, so the long-range case is never exercised
   — the first run reported "1.000× size, no difference" and the conclusion
   would have been that K4 was worthless. The data has to be *unique* across
   the first half and then repeated.
2. **`ZstdCompressor.compress()` shrinks the frame's window descriptor to fit
   the known content size**, so a 27-cap reader happily opened a "31-window"
   archive and the compatibility problem looked imaginary. `ZstdStage` uses
   `stream_writer`, where the size is unknown and the full requested window
   goes into the header. Only the streaming API reproduces the real behaviour.

### The real-data number is 4.40%

Two builds of the same installer, 642.9 MiB, forced through the stage:

| window_log | output | compress |
|---|---:|---:|
| 27 | 668,628,541 | 195.2 s |
| 31 | 639,241,730 | 195.9 s |

**4.40% smaller, no speedup at all.** And in the *actual pipeline* those MSIs
are high-entropy, so the analyzer routes them to `store` and the zstd stage
never sees them — K4 changes nothing for that job.

So there are three honest numbers, not one: **49.9%** is what a wide window is
worth when the duplicate is exact, **4.40%** is what it is worth on two versions
of a real installer, and **0%** is what it is worth on already-compressed input,
which is most of the Programs corpus. The roadmap's "🎁 free win" framing
described only the first.

### The window is fitted to the input, not pinned at the maximum

A window larger than the data cannot find matches the data does not contain.
Same 300 MiB corpus, three windows:

| window_log | window | output | compress | peak |
|---|---:|---:|---:|---:|
| 29 | 512 MiB | 157,699,989 | 54.0 s | **1,045 MiB** |
| 30 | 1 GiB | 157,699,989 | 71.5 s | 1,289 MiB |
| 31 | 2 GiB | 157,699,989 | 55.0 s | 1,814 MiB |

**Byte-identical at all three.** So `_window_log_for()` rounds the input size up
to the next power of two and clamps it to [27, 31]: the full ratio win for
**769 MiB less memory**, with the floor keeping small jobs exactly where they
were before K4.

### The actual defect

`extract` computed `max_window_size = 1 << self.long_log`, so **a build could
only ever read archives as wide as it writes**. Confirmed on streamed frames:

```
a 27-cap reader given a 31-window frame:
    ZstdError: Frame requires too much memory for decoding
a 31-cap reader given a 27-window frame:
    fine
```

The read ceiling is now a module constant independent of the write setting, and
raising it is genuinely free — measured **14 MiB** peak for a 27-byte frame
under a 2 GiB ceiling, because `max_window_size` is a refusal threshold, not an
allocation. Reading a genuinely wide frame costs +171 MiB (146 → 317).

`excmp/ram.py` models LZMA2 dictionaries only, so none of these zstd figures
reach the GUI's peak-RAM column. Known gap, not fixed here.

## 5. K5 — a read-only file stranded a whole scratch directory

Found by *listing the temp directory* after K1's end-to-end run, not by any
assertion. Two abandoned folders, each holding the same 11 files:

```
excmp-verify-i05n75qg/restore/.../rn_first_app/.git/objects/18/1f3cee...
    attrs = ReadOnly, Archive
```

Git writes loose objects **read-only**, and `shutil.rmtree(ignore_errors=True)`
cannot delete a read-only file on Windows — it swallows the error and walks
away. Reproduced standalone:

```python
os.chmod(f, stat.S_IREAD)
shutil.rmtree(d, ignore_errors=True)
d.exists()      # True, with objects/18/deadbeef still in it
```

So every compress or extract of a tree containing a `.git` left debris, at
**11 call sites** that all passed `ignore_errors`. `excmp/tempclean.py`'s
`rmtree_force` clears the read-only bit and retries; `ignore_errors` was never
the mistake by itself (cleanup runs in `finally:` blocks and must not raise) —
the mistake was that it was doing double duty as "handle the expected error",
and the expected error had a fix.

`test_the_stdlib_really_does_leave_a_read_only_file_behind` pins the *premise*,
so if a future Python fixes this the workaround can be retired rather than
carried forever for a reason nobody can check.

Why 945 tests were green over it: **D3 already asserts temp is clean, and D2
already round-trips read-only attributes. Neither crosses the two.** That is the
defect class — each half tested, the intersection not.

## 5b. K2 re-introduced K1's defect, in the phase that documented the rule

The most instructive finding of the session, and it was **predicted before it
was looked for** - which is the only reason it was caught before the commit.

K1's whole lesson, written into `manifest.py` beside `_MANIFEST_ENTRY_BYTES`,
is: *any new ledger key has to be added here, or `manifest_size_estimate`
under-reads and the refusal lands back at `write_container` after every byte is
written.* K2 dutifully bumped that constant 120 -> 152 for `mtime_ns`.

K2 also added `dirs` - **a new top-level field, unbounded, one full relative
path per empty directory** - and the estimate only ever iterated *file* paths.
Measured, 20,000 empty directories beside 10 files:

| | bytes |
|---|---:|
| preflight predicted | 14,498 |
| actually written | **1,550,859** |
| the `dirs` field alone | 1,548,889 |

**0.009x - a 100-fold under-read.** The guidance was followed to the letter for
the field it named and missed entirely for the field it did not, because the
rule had been written as "new ledger key" rather than "new manifest bytes".

Fixed by giving `manifest_size_estimate` a `dirs` parameter and passing
`empty_dirs` from `engine.compress`. Pinned by
`test_the_size_estimate_counts_the_empty_directory_list`.

Worth generalising, because this is now the third occurrence in three sessions
(K1's `same_as`, K1's non-ASCII escaping, K2's `dirs`): **a preflight that
models a document field-by-field will be wrong the next time a field is added.**
The durable fix is not another constant - it is to compare the estimate against
a genuinely serialised manifest in a test, which is what all three of those
tests now do.

## 5c. Four more defects, found by auditing the diff before committing it

An adversarial audit of the uncommitted K2-K5 diff - four lenses, each required
to *run* code rather than read it - found four real defects in K3 alone. All
four were reproduced by execution, and one is a regression the diff introduced.

### 1. The plain export silently dropped locked files (critical, a regression)

`_collect` no longer *raises* on an unreadable file; it returns a `skipped`
list. `compress_standard` bound that list and then consumed it **only** in the
"nothing readable at all" branch. So with *some* files locked it published the
`.7z`/`.zip` and said nothing anywhere: no field on `StandardResult`, no
warning, nothing in the CLI payload, and `gui/queue_manager.py` rebuilt the
result with `warnings=[]`, discarding even a future field.

Verified by running it: archive published, `verified: 5`, `7z l` listing five
files, the sixth absent and unmentioned. **Before this diff the same input
failed loudly**, because `analyze_file` opened the file and raised. The
product's own docstring calls this "the worst outcome this program can
produce", so a diff that introduced it needed catching before the commit.

Fixed: `StandardResult.skipped`, populated, plus reporting in the CLI and the
GUI, and the missing `copy2` guard on that path.

### 2. A locked *store-route* file still killed the whole job (major)

K3's first pass guarded three reads - `analyze_file`, `hash_file`, and the
pipe-route `copy2`. A store-route file is never staged: **its bytes are first
read inside `write_container`**, at `jpeg.pack(read_bytes())` and
`zf.write(src, ...)`, neither of which can drop a file. So the exact failure K3
exists to remove was still live for stored files.

Not an edge case, the *likely* half: CLAUDE.md records the analyzer putting
**41.9% of the real 6.4 GB corpus's bytes** on the store route. Verified by
locking a store-route file immediately after it was hashed - the real race -
which produced a raw `PermissionError` and no archive at all.

Fixed by probing each stored source with a one-byte read before the container
is built, in `compress()` rather than in `write_container`, so the
ledger/route/`stored_map` bookkeeping stays in one place.

### 3. `compress()` could publish an archive containing nothing (major)

The `if not ledger` guard ran only after the hash loop, but the staging copy
(and now the store probe) can empty the ledger too. With every piped file
failing there and no store route, the job published a container holding only
`manifest.json` and an empty payload - and **because its ledger is empty,
`excmp verify` passes on it forever**, reporting 0 verified files as success.

`compress_standard` had refused this since it was written, with the comment
*"a gate that can pass having checked nothing is not a gate"*. `compress()` had
no equivalent. Verified by making every `copy2` fail: `PUBLISHED. orig_bytes=0
final=626`, ledger entries 0, `list_archive(...).entries == []`.

### 4. Skip messages named only the basename (minor)

`describe_unreadable` built every sentence from `path.name`, so on any real tree
with repeated basenames - `node_modules`, per-folder `index.js` - two different
skipped files produced **byte-identical sentences**. For a message whose entire
purpose is that "a skip nobody is told about is worse than a failure", a name
the user cannot resolve to a file is most of the way back to silence: they
cannot go and re-archive it. Now labelled with the archive-relative path.

### What the audit confirmed was *not* broken

Worth recording, because it is the half that stops a fix from wandering:
`orig_bytes` is honest after every drop (measured at all three drop windows);
the ledger, `routes[].count`, `store_reasons`, `piped_bytes`, `pipe_route.files`
and `stored_map` all stay consistent; no half-written staging file is tarred in;
D9 still passes correctly with skips because `verify_restore` iterates the
ledger only; the EXTREME profile and `--password` both handle a locked file; and
both preflights err high, which is the safe direction.

## 6. A process note: do not benchmark and test at the same time

The full suite failed once during this session with

```
zstandard.backend_c.ZstdError: zstd decompress error: Allocation error : not enough memory
```

on `test_edge_cases.py::test_an_awkward_name_survives_a_roundtrip[leading-dash]`
— a tiny file. It passes in isolation. The cause was **this session's own
concurrent memory benchmarks** (1.8 GiB resident) plus a 642 MiB end-to-end
running alongside a 2-core machine's test suite.

Recorded because the same contention almost certainly widened the manifest
parse-time range reported in the K1 benchmark (1.2–1.7 s), and because a
transient allocation failure in a compression test is exactly the kind of thing
that gets misdiagnosed as a real defect. **Serialise the heavy runs.**
